# SpecForge Future Capability Registry

> **Status**: ACTIVE / NON-AUTHORITATIVE ROADMAP RECORD  
> **Purpose**: Preserve deferred product ideas and design intent so they are not lost during current-scope convergence.  
> **Authority boundary**: This document is **not** the current product specification, release scope, implementation plan, or acceptance baseline. Nothing in this registry becomes a current requirement unless the SpecForge product owner explicitly promotes it into the authoritative product specification through a later product decision.  
> **Created during**: Authority Model Recovery  
> **Baseline at creation**: `main@8f9824009f34bc4db93a0aa3a3b7883e8dbec4d9`

## 1. Governance rules

This registry exists to preserve good ideas that are intentionally deferred while the current product is simplified and stabilized.

Rules:

1. A registry entry is a **future candidate**, not an active product requirement.
2. Deferred capabilities MUST NOT be added to current release scope, release gates, installer assets, runtime exports, or acceptance criteria merely because they appear here.
3. Existing historical designs, Kiro specs, ADRs, standards, reports, and implementation artifacts referenced by an entry remain source material only unless separately promoted.
4. Promotion into the current product requires an explicit product-owner decision and an update to the authoritative product specification.
5. When an item is revisited, the team must re-evaluate it against the then-current architecture rather than blindly implementing the old design.
6. When a future capability is promoted, this registry should retain the historical entry and record the promotion decision instead of deleting the original rationale.
7. This registry should favor preserving design intent, constraints, known risks, source references, and re-entry criteria over preserving obsolete implementation details.

Status values used here:

- `FUTURE_CANDIDATE`: worth preserving for future product expansion.
- `PARKED`: intentionally inactive; reconsider only if a concrete need appears.
- `PROMOTED`: later moved into the authoritative product specification.
- `REJECTED`: explicitly abandoned as a future direction, while history remains auditable.

## 2. FCR-001 — Project Spec multi-view architecture

**Status**: `FUTURE_CANDIDATE`  
**Origin**: v1.2/v1.14/v1.3 Project Spec architecture work  
**Current product decision**: Do not enable the full multi-view system now. Keep the current Project Spec core and only absorb mature core governance rules.

### Preserved idea

As SpecForge matures, a single `architecture.md` plus module requirements/design may become insufficient for large systems. A future Project Spec can support controlled, explicit architectural views without turning every project into a large mandatory document set.

Candidate structure:

```text
.specforge/project/
  architecture.md
  requirements_index.md
  design_index.md
  glossary.md
  decisions.md
  trace_matrix.md
  extension_registry.json
  modules/
  views/                  # conditional, not generated by default
  decisions/              # conditional ADR detail
```

### Capabilities worth preserving

- Core / Conditional / Optional Project Spec file classes.
- `.specforge/project/views/**` for project-level specialist views.
- `decisions.md` as the core decision index.
- `decisions/ADR-*.md` as conditional ADR detail, created only after registration.
- `extension_registry.json` as the registration point for new `view_type`, `gate_type`, `artifact_type`, and `workflow_path`.
- View → Gate → Trace linkage.
- No automatic generation of empty specialist files.
- Specialist views appear only when impact analysis proves they are useful.
- Module detail remains under `.specforge/project/modules/<MODULE_CODE>/**`; views must not become a second module-spec system.

### Candidate future views

The following ideas are preserved as possible future views or governed extensions, not current requirements:

- domain model
- context map
- cross-cutting concepts
- architecture risks / technical debt
- service catalog / service boundary
- C4 impact and architecture layers
- quality attributes / ATAM-style analysis
- resilience patterns
- runtime delivery / operational readiness
- SRE / SLO / observability view
- architecture evolution / fitness functions
- data architecture
- distributed-system or cloud-specific concerns

### Re-entry criteria

Reconsider this capability when most of the following are true:

- the current Project Spec core has been stable for a meaningful period;
- `extension_registry.json` has a proven production lifecycle;
- Path Service / Path Policy / Write Policy have a single authoritative implementation;
- Candidate/Gate/User Decision/Merge/Trace are stable and well tested;
- real projects demonstrate repeated architecture information that does not fit cleanly in the current core files;
- adding a view solves a demonstrated problem rather than merely improving theoretical completeness.

### Important constraint

Do not promote the entire old v1.3 document wholesale. Future adoption must be incremental and capability-driven.

## 3. FCR-002 — OpenClaw integration

**Status**: `FUTURE_CANDIDATE`  
**Current product decision**: OpenClaw is not part of the current SpecForge product scope.

### Preserved idea

SpecForge may later support OpenClaw or similar automation/IM platforms as external clients.

Preferred architectural direction:

```text
OpenClaw / automation platform
        ↓
stable SpecForge CLI JSON or Daemon HTTP/SSE contract
        ↓
Daemon
        ↓
OpenCode Adapter
        ↓
OpenCode
```

### Constraints to preserve

- OpenClaw must not write SpecForge state directly.
- OpenClaw must not duplicate Permission, Workflow, Gate, or state-machine rules.
- OpenClaw must not directly couple to OpenCode internals when a stable SpecForge contract exists.
- The bridge should remain an integration layer, not become a second SpecForge runtime.
- Existing `.kiro/specs/openclaw-integration/**`, `.kiro/specs/openclaw-skill-bridge/**`, and related CLI integration documents are historical/future design sources only.

### Re-entry criteria

Reconsider when the Daemon public API, CLI machine mode, authentication model, OpenCode Adapter, and service deployment model are stable enough to support an external automation client without special-case bypasses.

## 4. FCR-003 — Multimodal input

**Status**: `FUTURE_CANDIDATE`  
**Current product decision**: Remove Multimodal from current product scope.

### Preserved idea

Future SpecForge versions may accept non-text user input through a unified message model.

Potential staged direction:

1. stable unified `UserMessage` contract;
2. text path remains canonical;
3. unsupported content fails closed deterministically;
4. later add explicit image/audio/file capabilities only when there is a real consumer;
5. OCR, transcription, media parsing, and model-specific preprocessing remain separate optional capabilities.

### Constraints to preserve

- Non-text support must not leak provider-specific media shapes into core governance contracts.
- File/blob handling needs explicit size, persistence, security, and evidence rules.
- Multimodal support should be attached to a real Daemon/OpenCode Adapter ingestion path before it is considered a product capability.
- “Package exists” or “tests pass” is not sufficient evidence that the capability is enabled.

### Re-entry criteria

Reconsider only after the current text-only product path is stable and a real product use case requires non-text input.

## 5. FCR-004 — Self-Healing / automated diagnosis and recovery

**Status**: `FUTURE_CANDIDATE`  
**Current product decision**: Remove Self-Healing from current product scope.

### Preserved idea

A mature SpecForge could later help diagnose governance or runtime failures and propose safe recovery actions.

Possible staged model:

```text
Detect
  ↓
Diagnose (read-only)
  ↓
Propose
  ↓
User / policy approval
  ↓
Apply through existing controlled Tools
  ↓
Verify
  ↓
Record evidence
```

### Constraints to preserve

- Start with read-only diagnosis; do not jump directly to autonomous repair.
- Self-Healing must reuse existing Permission, Write Guard, HardStop, Gate, state, and evidence mechanisms.
- It must not create a parallel recovery state machine.
- Any mutating repair must use normal controlled Tool and approval boundaries.
- Risk tiers and explicit approval requirements should be part of any future design.
- Recovery history must remain auditable.

### Re-entry criteria

Reconsider when the core runtime, diagnostics, error taxonomy, HardStop recovery, permissions, and evidence model are stable enough that automated diagnosis will reduce complexity instead of creating a second control plane.

## 6. FCR-005 — Third-party Plugin / Extension runtime

**Status**: `FUTURE_CANDIDATE`  
**Current product decision**: Remove `@specforge/plugin-loader` and third-party runtime plugin loading from current product scope. This does **not** remove the SpecForge OpenCode Thin Plugin, which is a separate first-party integration component.

### Preserved idea

A future mature product may support third-party extensions.

Potential future capability set:

- extension manifest schema;
- declared permissions;
- static source validation;
- compatibility/version contract;
- signed or trusted distribution model;
- runtime isolation;
- sandbox / IPC boundary;
- lifecycle and resource limits;
- explicit install/enable/disable operations;
- observable failure and recovery behavior;
- extension-specific Gate / evidence rules where needed.

### Constraints to preserve

- Thin Plugin and third-party Plugin Loader must remain distinct concepts.
- Static validation alone must not be presented as a complete secure runtime plugin system.
- Dynamic loading, hot reload, sandboxing, IPC, and process management should be introduced only as one coherent security model.
- Unknown extensions should fail closed.
- Future extension support should integrate with `extension_registry.json` rather than create a parallel registry.

### Re-entry criteria

Reconsider only when there is a concrete third-party extension ecosystem requirement and the Permission / Write Guard / installer / runtime isolation model is mature.

## 7. FCR-006 — Data/schema migration and legacy conversion

**Status**: `PARKED`  
**Current product decision**: The Migration module is removed from the current product.

### Preserved idea

The project may eventually need controlled conversion when a real incompatible persistent-data change occurs. The current decision removes the standing Migration product module; it does not assert that data conversion can never be needed.

Possible future forms should be evaluated only when a real compatibility problem exists:

- a one-time external conversion utility;
- per-file owner-managed schema conversion;
- explicit backup + conversion + verification flow;
- release-specific conversion tooling.

### Constraints to preserve

- Schema validation is not the same thing as migration and must not be hidden inside a future Migration module.
- No automatic legacy conversion should be introduced without a new product decision.
- Conversion must have explicit source and target contracts.
- Old formats must not silently become a second runtime truth.
- A future converter should be as narrow as the real compatibility need.

### Re-entry criteria

Reconsider only when an actual supported persistent format change cannot be handled by normal current-format validation and requires a deliberate compatibility path.

## 8. Promotion protocol

When the product owner decides to activate a future capability:

```text
Future capability entry
        ↓
fresh architecture/evidence review
        ↓
explicit product-owner promotion decision
        ↓
authoritative product specification update
        ↓
implementation plan
        ↓
tasks
        ↓
verification / acceptance
```

The historical entry remains in this registry with:

- promotion date;
- product decision reference;
- authoritative specification location;
- scope actually promoted;
- portions deliberately left deferred.

This prevents future development from losing useful historical ideas while also preventing old designs from silently becoming current authority.
